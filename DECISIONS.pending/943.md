### 20. A subscription asks for what the extensions read as well

The Process-Engine-API hands a task to exactly one subscription. An extension therefore gets no
subscription of its own. It reads what this adapter's subscription delivered, through a
`PeaUserTaskObserver`. Until now that subscription asked only for the variables of the
`@WorkflowTask` methods (decision 7). A `@TaskParam` of an extension's method, for example a details
provider of the Business Cockpit, got its value only where a workflow method read the same variable.
Otherwise it got `null`.

`fetchVariablesOf` now also asks the core `WorkflowTaskWiring#extensionTaskParameterNames` for
every task it serves, and the subscription fetches the union. The core answers over every extension
which registered a handler contract, so the adapter needs to know nothing about the extensions.

The keys go in the order an extension looks a task up by: the BPMN element id first, then the task
definition. That is the order of the Business Cockpit, so the variables fetched are those of the
method which runs there. A task of a process nobody deployed has no element id, so it is asked by
its task definition alone.

The question is asked for service tasks as well as for user tasks. An observer sees user tasks
only today, but the core answers the same question for both, and a service task an extension never
reads costs nothing: the answer is empty.
